# MoM 제품 목적과 요구사항

[문서 인덱스](README.md) · 기록 기준일 2026-09-30

MoM의 목적은 MacBook, Android 등에서 얻은 긴 회의 녹음을 정확한 전사와 활용 가능한 회의록으로 바꾸는 것이다. 한 번 만든 전사문을 다시 활용해 출력 언어, 회의록 구성과 모델을 바꿀 수 있어야 한다. 정확성을 검토할 근거를 남기면서 모델 비교도 할 수 있는 도구를 지향한다.

## 해결하려는 문제

1~2시간 이상 녹음을 그대로 AI에 보내면 파일 크기 제한, 긴 처리 시간, 브라우저 메모리와 재시도 비용이 문제가 된다. 녹음을 여러 번 변환하거나 전사하면 비용과 정보 손실이 누적된다. 따라서 파일 준비, 전사, 전사 검토, 회의록 생성의 단계를 구분하고 완료된 결과를 활용하는 구조가 필요하다.

회의에서는 여러 언어가 섞이고, 같은 주제가 나중에 다시 등장하며, 앞선 결정을 뒤집기도 한다. 녹음의 시간 단위로 잘랐다는 이유로 각 청크를 독립된 주제나 최종 결정으로 취급하면 회의록이 왜곡된다. 출력이 자연스럽더라도 발언·담당자·기한의 근거가 없는 회의록은 신뢰하기 어렵다.

설치형 앱은 배포와 사용자 설치 부담이 있다. 사용자가 웹에서 코드와 리소스를 받아 자신의 파일을 처리하는 데스크톱 브라우저 중심 앱을 우선한다. 녹음이 모바일 기기에서 만들어졌다는 것과 모바일 브라우저에서 긴 파일 처리가 보장된다는 것은 다른 요구다.

## 확정 요구사항 CONFIRMED REQUIREMENTS

| ID | 요구사항 | 해석과 범위 |
| --- | --- | --- |
| C01 | 이름은 mom 또는 MoM | Minutes of Meeting이라는 직관적인 의미를 채택했다 |
| C02 | 긴 회의 녹음을 회의록과 지식으로 활용 | 1~2시간 이상 녹음이 주요 사용 사례이며 무제한 길이 보장은 아니다 |
| C03 | 데스크톱 브라우저 중심 웹앱 | 별도 설치 앱의 배포와 사용 부담을 줄인다 |
| C04 | MoM 로그인과 애플리케이션 서버 저장소를 두지 않는 방향 | 로컬 파일 준비·결과 관리, 사용자 키, 제공자 직접 호출을 기준으로 한다 |
| C05 | 원본 녹음에서 필요에 따라 오디오를 준비한 뒤 청크별 STT | 영상은 오디오만 추출하고, 변환은 필요한 경우에 수행한다 |
| C06 | STT 원시 반환 결과와 시간 매핑·처리 상태를 로컬에 남기는 처리 흐름 | 원문과 합친 전사문을 구분한다. 보관 기술과 수명은 제안 단계다 |
| C07 | 여러 예상 입력 언어를 선택 | 언어가 섞인 회의를 고려한다. 특정 언어 목록으로 제품을 제한하지 않는다 |
| C08 | 회의록 출력 언어는 입력 언어와 별도로 선택 | 한국어 출력으로 고정하거나 선택하지 않은 입력 언어를 버리지 않는다 |
| C09 | 회의록에 포함할 항목을 사용자가 선택 | 예를 들어 요약과 할 일만 선택할 수 있어야 한다 |
| C10 | 회의록의 목표 출력 형식은 항상 Markdown .md | 항목 선택은 내용 구성의 변경이며 파일 형식 변경이 아니다 |
| C11 | 결과를 검토·편집하고 로컬로 내보내는 흐름 | 공개 게시나 자동 전송은 포함하지 않는다 |
| C12 | STT와 회의록 모델을 시험·비교하려는 목적 | 비교 화면·동시 실행·첫 릴리스 포함 수준은 미결정이다 |
| C13 | Cloudflare 호스팅 계획 | 사용자가 Vite React Template으로 프로젝트를 만들려는 방향을 밝혔다. 템플릿 커밋은 확인했고 배포 성공은 확인하지 않았다 |
| C14 | 앱이 보관하는 민감한 로컬 데이터를 실제로 암호화 | 오디오 청크, 전사, 회의록, 제목·메타데이터를 포함한다. 공개 암호화 파라미터는 구분한다 |
| C15 | 비밀값으로 앱 잠금과 해제 | 화면 가림·잠금 안내와 암호화 저장을 함께 요구한다. 단순 blur로 대체하지 않는다 |

`wa`에서 얻는 녹음도 언급됐다. WhatsApp을 뜻할 가능성이 있으나 서비스명, 다운로드 방식, 컨테이너와 코덱은 확정하지 않았다. 이 표기는 포맷 지원 선언으로 사용하지 않는다.

## 제안 PROPOSALS

| ID | 제안 | 이유와 남은 조건 |
| --- | --- | --- |
| P01 | 표시 이름 MoM · 회의록 만들기 | 이름 옆에서 기능을 바로 설명한다. 표시 문구는 최종 선택 전이다 |
| P02 | React + Vite + TypeScript와 Workers Static Assets | 브라우저 중심 UI와 정적 배포에 맞는 권장 스택이다. 실제 로컬 앱 소스는 아직 확인되지 않았다 |
| P03 | 초기 지원 브라우저 Chrome과 Edge | 제한된 Chromium 실험을 출발점으로 삼는다. 제품 브라우저 지원은 별도 검증해야 한다 |
| P04 | 10~15분 청크와 10~15초 겹침 | 긴 녹음 처리와 경계 문맥 확보의 출발값이다. 10초 청크라는 뜻이 아니다 |
| P05 | OpenAI STT와 OpenRouter 회의록 생성 | 직접 브라우저 호출을 유지하면서 전사와 텍스트 모델 시험을 분리하는 작업 설계다 |
| P06 | 키를 세션 메모리에만 보관 | 영구 키 저장의 위험을 줄이는 권장안이다. 확정된 사용자 선택은 아니다 |
| P07 | 실패 청크만 재시도하고 완료분을 보존 | 긴 녹음 전체를 다시 보내는 시간·비용을 줄인다 |
| P08 | 취소·재개·체크포인트와 백업 가져오기 | 중단 시 작업과 전사문을 회복하기 위한 제안이다. 구현·내구성 검증은 남아 있다 |
| P09 | 회의록 프리셋과 항목 순서 변경 | 요약과 할 일, 표준, 상세 등을 제안한다. 이름·항목·순서는 고정하지 않았다 |
| P10 | 추가 지시와 로컬 템플릿 저장 | 반복 회의의 형식을 재사용하려는 안이다. 첫 릴리스 포함 범위는 미결정이다 |
| P11 | 전사문 편집 및 원시 결과·전사문 백업 | STT 오류를 고치고 결과의 이동성을 확보한다. 원시 결과를 덮어쓰지 않는다 |

이 제안들은 디자인과 구현 계획의 후보로 사용할 수 있지만, 전부 첫 릴리스에 포함된다는 약속은 아니다. [디자인 기능 목록](07-design-feature-inventory.md)에 제시한 화면도 같은 원칙을 적용한다.

## 대표 사용 시나리오

### 긴 다국어 회의를 문서로 남기기

사용자가 2시간 녹음을 가져온다. 앱은 파일 정보를 검사하고, 예상 입력 언어를 여러 개 선택하게 한다. 필요한 경우에만 오디오 추출·변환·압축을 수행해 크기 제한에 맞는 청크를 준비한다. 외부 전송을 확인한 사용자가 STT를 실행하고, 완료된 전사와 경계의 불확실한 부분을 검토한다. 출력 언어와 원하는 항목을 선택한 뒤 회의록을 편집하고 `.md`로 저장한다.

한국어·영어·인도네시아어는 논의에서 등장한 회의 예시다. 이 세 언어만 지원하기로 정한 것은 아니다. 예상 언어 선택을 실제 API의 단일 또는 복수 힌트로 어떻게 전달할지는 모델 능력에 따라 정한다.

### 동일 전사문에서 회의록 구성을 바꾸기

첫 회의록에서 상세 논의가 필요했지만 나중에는 요약과 할 일만 필요할 수 있다. 또는 다른 언어로 공유용 문서를 만들 수 있다. 이미 저장한 선택 전사문을 활용해 텍스트 생성만 다시 실행하는 방향을 기준으로 한다. 출력 언어·항목 변경을 이유로 STT 전체를 반복하지 않는다. 새로운 생성에는 별도의 텍스트 모델 비용이 발생할 수 있다.

### 비교 목적의 별도 실행

전사 품질을 비교할 때는 동일 오디오 청크와 동일 전처리 조건을 사용한다. 회의록 품질을 비교할 때는 동일한 선택 전사문과 지시를 사용한다. 서로 다른 전사문에서 만든 회의록의 차이를 텍스트 모델 성능 차이로 단정하지 않는다. 비교 실행의 경위와 조건은 [제공자와 비교](05-providers-and-comparison.md)에 정의한다.

## 권장 첫 릴리스 범위

**제안:** 첫 릴리스는 파일 가져오기 → 로컬 준비 → 청크별 STT → 원시 결과 저장 → 시간축 병합·검토 → 선택 가능한 회의록 항목 → 편집과 `.md` 내보내기의 완결성에 집중한다. 새로 확정한 암호화 저장·잠금 요구도 범위와 출시 조건에 반영한다. 처리 상태를 숨기지 않고, 부분 실패에서 완료분을 활용하는 것이 핵심이다.

최소 화면은 [디자인 목록](07-design-feature-inventory.md)의 여섯 화면을 반드시 여섯 페이지로 구현하는 방식일 필요는 없다. 핵심 사용 흐름은 가져오기, 전사 검토, 회의록 생성으로 묶고, 진행 상태와 제공자 설정은 필요한 시점에 보여줄 수 있다.

모델 비교는 제품 목적에 포함하지만 첫 릴리스에서는 하나의 청크 또는 하나의 전사문에 대한 명시적인 추가 실행으로 제한하는 안을 권장한다. 여러 모델을 자동·동시에 전체 녹음에 호출하는 기능은 비용과 복구 범위를 크게 늘리므로 별도 결정한다.

## 현재 범위 밖의 후보

실시간 녹음, 회의 실시간 참가, 팀 협업, MoM 계정, 클라우드 동기화, 과금·결제 연동, 외부 캘린더·메신저 자동 전송은 지금의 첫 릴리스 범위로 승인되지 않았다. 가격 정책이나 수익 모델도 정하지 않았다. 향후 필요할 때 새 요구사항으로 검토한다.

## 미결정 OPEN QUESTIONS

지원 파일 조합, 초기 STT·텍스트 모델, 제공자 구성의 최종 채택, 첫 릴리스 비교 기능, 임의 Markdown 템플릿 붙여넣기, 저장 수명, 지원 브라우저·장비와 품질 기준이 남아 있다. 임의 Markdown 템플릿을 첫 버전에 넣을지 질문한 적은 있지만 답은 확정되지 않았다. 질문의 구체적인 선택지는 [결정 기록](09-decisions-and-roadmap.md)에 모았다.
