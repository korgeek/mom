# 개인정보와 암호화된 로컬 보관

[문서 인덱스](README.md) · [구조와 데이터](02-architecture-and-data.md) · 기록 기준일 2026-09-30

**확정 요구사항 CONFIRMED REQUIREMENTS:** MoM 애플리케이션 서버에 회의 자료를 보관하지 않는 방향이며, 앱이 보관하는 민감한 로컬 데이터는 실제로 암호화한다. 비밀값으로 앱을 잠그고 해제하며 화면 가림과 잠금 안내도 제공한다. PIN이 제안됐지만 길이·강도와 구체적인 암호화 설계는 확정하지 않았다.

**2026-10-18 최신 사용자 결정:** 기본은 `표준 · 작업 이어가기`다. 화면잠금은 민감 화면과 새 명령을 막고 승인된 녹음·준비·전사·정리를 이어가며, 잠긴 상태에서 마지막 작업 저장 후 키 참조를 해제한다. `엄격 · 잠글 때 작업 중지`는 화면잠금 또는 `visibility hidden`에서 작업을 중단하고 저장 가능한 완료분을 보존한다. 두 모드의 저장 암호화는 같다. 표준 실행 중 키/민감 데이터의 탭 메모리 유지, 브라우저/OS 중단 및 종료 시 비동기 저장 한계를 구분한다. 이전 즉시 숨김 잠금/잠금 시 모든 작업 중단 요구를 이 정책으로 대체한다. 기본 60초와 60/180/300/600/1800/3600초/사용 안 함 설정·정책·미적용 편집은 암호화 저장한다. ## 데이터 위치와 전송

| 데이터 | 처리·보관 위치 | 외부 전송 |
| --- | --- | --- |
| 앱 코드와 리소스 | Cloudflare 호스팅에서 브라우저로 내려받음 | 웹 접속에 따른 요청 메타데이터가 생길 수 있음 |
| 원본·준비 오디오 | 로컬 처리, 앱에 보관하는 사본은 암호화 | 선택한 청크를 STT 제공자로 보냄 |
| 원시 전사·합친 전사·회의록 | 암호화된 로컬 저장과 잠금 해제 중 사용 | 전사문·지시를 텍스트 제공자에 보냄 |
| 제목·파일명·설정·작업 상세 | 민감 메타데이터도 암호화 | 필요한 제공자 요청 필드 외 전송을 최소화 |
| 사용자 API 키 | 세션 메모리 보관 권장안 | 해당 제공자의 인증에 사용 |
| 내보낸 Markdown | 사용자가 저장한 일반 파일 | 사용자의 후속 공유·보관에 따름 |

파일 준비가 로컬이라는 사실과 AI 추론이 외부라는 사실을 함께 설명한다. 완전 오프라인, 모든 데이터가 로컬에만 있음, 외부 보관 없음이라고 표시하지 않는다. OpenRouter는 실제 하위 제공자도 데이터 경로에 포함한다. 외부 제공자의 보관 정책과 로컬 암호화는 서로 다른 통제다.

[OpenAI 데이터 안내](https://developers.openai.com/api/docs/guides/your-data)에 따르면 학습 사용 여부와 보관·로그 정책은 별개다. 선택 API·모델·계정 설정을 확인해야 하며, 학습에 쓰지 않는다는 설명을 아무 데이터도 보관하지 않는다는 뜻으로 바꾸지 않는다.

## 위협 모델

암호화 저장의 주요 목표는 공격자가 브라우저의 저장 파일·백업 바이트를 가져가도 비밀값 없이 회의 내용을 읽기 어렵게 하는 것이다. 민감한 제목이나 메타데이터도 평문 검색 인덱스·캐시·로그에 남기지 않아야 한다. 실제 저장소를 복사해 평문 흔적을 확인하는 시험이 필요하다.

다음 경계는 별도로 설명한다. 원래 사용자의 원본 파일, 사용자가 내보낸 평문 `.md`, 외부 AI가 받은 자료는 MoM 저장소 암호화의 보호 범위 밖이다. 잠금 해제 중 XSS·변조된 앱 코드·악성 브라우저 확장·운영체제나 장비 장악은 평문과 키에 접근할 수 있다. 단순 잠금이나 암호화로 이를 모두 해결한다고 주장하지 않는다.

## 암호화 저장소 설계 제안 PROPOSALS

무작위 데이터 키로 저장 내용을 암호화하고, 사용자 비밀값에서 유도한 키로 데이터 키를 감싸는 구조를 후보로 둔다. 비밀값 변경 시 전체 오디오를 다시 암호화할 필요를 줄일 수 있으나 키 교체·원자적 저장·실패 복구를 검토해야 한다.

AES-GCM과 Web Crypto API는 후보이며 확정 구현이 아니다. 레코드·청크마다 올바른 nonce 관리, 인증 태그 검증, 레코드 식별자·버전과의 결합, 잘못된 암호문 처리와 원자적 쓰기 설계가 필요하다. 단순히 AES라는 이름을 채택해 안전하다고 선언하지 않는다. [MDN Web Crypto 안내](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API)와 [OWASP 암호화 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)을 참고해 구현 전에 검토한다.

salt, KDF 파라미터, 스키마·암호화 버전과 필요한 nonce 같은 값은 공개일 수 있다. 암호문 크기나 레코드 존재 등의 정보도 남을 수 있다. 앱의 민감한 내용·메타데이터를 암호화하는 요구를 모든 바이트와 존재 정보까지 숨긴다는 약속으로 설명하지 않는다.

## 비밀값과 PIN

강한 암호문을 권장한다. 4~6자리 숫자 PIN은 저장 바이트를 복사한 공격자가 앱 UI의 시도 횟수 제한을 우회해 오프라인으로 반복 시험할 수 있다. 화면에서 잠금 시도를 제한하는 것만으로 짧은 PIN이 강해지지 않는다.

검토할 KDF 후보는 Argon2id와 PBKDF2다. 브라우저 구현 방식, 의존성, 메모리·시간 비용, 장비별 잠금 해제 지연과 공격 비용을 고려해 선택한다. 파라미터·최소 비밀값 기준은 미결정이다. 비밀값을 그대로 저장하거나 단순 해시를 암호화 키로 사용하는 설계는 후보로 삼지 않는다.

## 잠금 시 실제 동작

화면 blur와 모달은 어깨너머 노출을 줄이는 표현이다. 실제 잠금에는 민감 텍스트를 DOM·접근성 트리에서 제거하고 편집기·검색 결과·미리보기·오디오 재생 URL을 정리하는 처리가 필요하다. 제목까지 감춘 일반 잠금 화면을 제안한다.

잠글 때 새 외부 요청을 막고, 처리 Worker를 안전한 지점에서 중지하며, 완료 결과를 암호화해 저장하는 방향을 검토한다. 평문과 키 참조를 버리되 JavaScript의 GC와 브라우저 메모리 때문에 완전한 메모리 zeroization을 보장하지 않는다.

실행 중 STT 응답이 잠금 뒤 도착할 때의 정책은 미결정이다. 키를 내려놓기 전에 안전 체크포인트를 완료할지, 요청을 중단하고 결과 불명 상태를 남길지 정해야 한다. 잠금과 API 키 수명, 여러 탭의 잠금 동기화, 자동 잠금 시간·장비 절전 시 동작도 별도 결정한다. 한 탭만 잠겨 다른 탭에 평문이 남는 상태는 수용하지 않는 방향이다.

## API 키

세션 메모리만 사용하는 권장안을 유지한다. 영구 보관은 사용자 선택·정책 승인과 설계 검토 없이 추가하지 않는다. 잠금 해제 비밀값, 데이터 키, API 키는 서로 역할이 다르며 공유하지 않는다. 키를 코드·번들·URL·analytics·오류 추적·로그·Markdown 백업에 넣지 않는다. `localStorage`는 보안 키 보관함이 아니다.

외부 스크립트를 줄이고 CSP, 요청 대상 제한, 안전한 Markdown 렌더링과 의존성 관리를 검토한다. CSP가 허용된 앱 코드의 악용이나 잠금 해제 상태의 XSS 위험을 모두 없애지는 않는다. 운영 로그에는 헤더와 회의 내용 대신 필요한 최소 오류 정보만 남기는 안이다.

## 로컬 저장 실패와 백업

IndexedDB·OPFS는 후보이며 할당량·퇴거·시크릿 모드·사용자 삭제 영향을 받는다. [MDN 저장 안내](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)를 참고해 공간 추정, 쓰기 예외와 명시적 저장 실패를 처리한다. 암호화로 크기와 쓰기 방식이 달라지는 영향도 검증한다.

암호화 백업, 가져오기와 복구 키는 **제안**이다. 아직 승인된 기능이나 구현이 아니다. 비밀값과 사용 가능한 복구 수단을 모두 잃으면 데이터는 복구할 수 없다. MoM 계정·서버가 없으므로 관리자 비밀번호 초기화로 기존 데이터를 읽을 수 있다는 흐름을 만들지 않는다.

평문 Markdown 내보내기는 확정된 출력 방식이다. 내보내기 전 일반 파일로 저장된다는 점을 설명하고 사용자가 저장 위치·후속 공유를 결정한다. 암호화 백업이 추가되더라도 평문 `.md`와 구분한다.

## 보안 시험과 출시 조건

잘못된 암호, 변조·잘림 암호문, nonce 중복 방지, 중단된 쓰기·비밀값 변경, 복구 실패, 잠금 중 DOM·다른 탭·Worker 잔류, 저장소·로그·캐시의 평문 흔적을 시험한다. 오프라인 복사본 공격과 짧은 PIN의 한계를 검토한다. 알고리즘·파라미터와 구현 검토, 잠금 상태의 데이터 제거, 암호화 저장 검증을 통과하기 전에는 안전한 잠금 완료를 주장하지 않는다. 구체적인 행렬은 [출시 조건](08-verification-and-release-gates.md)에 연결한다.

## 2026-10-15 암호 최소 길이 변경

사용자가 사용성을 위해 보관함 암호의 최소 길이를 16자에서 **8자**로 낮추도록 요청했다. 새 보관함 생성·암호 변경 검증과 생성 화면의 안내·확인 입력·자동완성 규칙에 적용한다. 최대 256 Unicode 코드 포인트·1024 UTF-8 bytes, 숫자만으로 된 암호 거부, 공백·대소문자 보존은 유지한다. 기존 암호와 암호화된 데이터를 자동 변경하지 않으며, 암호화 형식과 KDF는 그대로다. 최소 길이를 만족해도 짧거나 예측 가능한 암호의 추측 공격 위험은 남는다. 긴 고유 암호 권장은 유지한다.
