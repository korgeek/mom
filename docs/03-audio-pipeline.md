# 긴 오디오 준비와 청크 처리

[문서 인덱스](README.md) · [데이터 설계](02-architecture-and-data.md) · 기록 기준일 2026-09-30

파일 준비의 목표는 STT에 유효한 오디오를 보내면서 원본 정보 손실과 브라우저 자원 사용을 제한하는 것이다. 아래 정책은 **제안 PROPOSALS**이며, 제한된 합성 MP3 실험을 모든 녹음의 지원 보장으로 확대하지 않는다.

## 파일 검사와 변환 순서

1. 사용자가 선택한 파일의 바이트 수, 컨테이너, 오디오 코덱, 길이, 채널과 샘플레이트를 확인한다. 확장자만으로 지원 여부를 확정하지 않는다.
2. 영상이면 오디오 트랙을 찾는다. 지원되는 오디오를 그대로 추출할 수 있으면 불필요하게 재인코딩하지 않는 안이다. 무음 영상이나 여러 오디오 트랙은 별도 선택·오류 처리가 필요하다.
3. STT 제공자가 받는 형식과 브라우저가 읽고 쓸 수 있는 형식의 교집합을 확인한다. 제공자 지원은 브라우저 변환 가능성을 뜻하지 않는다.
4. 시간축에 맞는 유효한 청크를 만들고, 전송 제한을 넘는 경우 필요한 압축·더 짧은 구간을 선택한다.
5. 최종 인코딩 파일의 실제 `Blob.size` 등 바이트 값을 검사한다. 유효한 헤더·컨테이너와 재생·디코딩 가능성도 확인한다.
6. 원본 구간과 인코딩 조건을 기록하고 암호화된 로컬 저장에 성공한 결과만 다음 단계에 사용한다. 저장·잠금 정책은 [보안 문서](06-privacy-and-local-storage.md)를 따른다.

MacBook·Android의 실파일과 `wa`의 파일 조합은 확인 전이다. M4A/AAC, Ogg/Opus와 긴 영상은 아직 실험하지 않았다. 특정 메신저의 파일을 모두 지원한다는 UI 문구는 사용하지 않는다.

## 청크 길이와 겹침

출발값은 **10~15분 청크에 10~15초 겹침**이다. 길이 단위는 분이고 겹침 단위는 초다. 10초짜리 수백 개 청크를 만드는 설계가 아니다. 겹침은 문장이 잘리는 손실을 줄이기 위한 것이며 STT 중복 비용과 전사 병합 부담도 발생시킨다.

설명용 계획에서 청크 길이를 `D`, 겹침을 `O`, 원본 길이를 `T`로 두면 시작 간격은 `D-O`이며 구간 끝은 `min(시작+D,T)`다. 이 방식을 선택하면 1시간·10분·10초 조건에 짧은 마지막 구간까지 7개, 2시간·15분·15초 조건에 9개가 생긴다. 실제 제품의 끝 구간 처리와 경계 이동 정책은 결정 전이다.

```text
10분 청크와 10초 겹침의 예
청크 1   00:00 ~ 10:00
청크 2   09:50 ~ 19:50
청크 3   19:40 ~ 29:40
```

무음이나 발화 종료 근처로 경계를 옮기는 방식은 향후 품질 시험 후 검토할 수 있다. 경계를 움직이면 실제 시작·끝·겹침 값을 저장해야 한다. 고정 시간으로 잘라도 청크 경계가 회의 주제의 경계라는 뜻은 아니다.

## 시간보다 실제 바이트가 제한 기준

2026-09-30 확인한 [OpenAI 파일 전사 안내](https://developers.openai.com/api/docs/guides/speech-to-text)는 파일당 25 MB 제한을 명시한다. 모델과 API의 제한은 실행 전에 다시 확인한다. 15분이라는 길이만으로 제한 충족을 판단하지 않는다.

| 형식 가정 | 겹침과 헤더를 제외한 계산 | 의미 |
| --- | --- | --- |
| 16 kHz 모노 16 bit PCM 15분 | 16,000 × 1 × 2 × 900 = 28,800,000 bytes | 약 28.8 MB이므로 25 MB보다 크다 |
| 같은 PCM 10분 | 16,000 × 1 × 2 × 600 = 19,200,000 bytes | 약 19.2 MB이나 실제 파일 검사와 여유가 필요하다 |
| 64 kbps 압축 오디오 15분 | 64,000 ÷ 8 × 900 = 7,200,000 bytes | 약 7.2 MB의 추정치이며 품질·가변 비트레이트·오버헤드는 별개다 |

표의 MB는 1,000,000 bytes 기준이다. 겹침을 추가하는 청크 계획이면 해당 시간도 포함해야 한다. API가 파일 크기와 전체 요청 크기를 어떻게 제한하는지 확인하고, 모델별 제한보다 작은 안전 목표값을 둔다. 안전 여유의 정확한 비율은 아직 선택하지 않았다.

처음에는 모노 64~96 kbps를 시험하는 안을 제안했다. 실제 다국어 발화·숫자·고유명사 정확도는 검증하지 않았다. 이미 형식과 크기가 적합하면 손실 압축을 반복하지 않는다. 스테레오는 발화자 분리 단서를 담을 수 있으므로 원본을 보존하고 모노 변환의 영향을 비교한다.

## 브라우저 메모리

2시간·48 kHz·스테레오·float32 PCM은 `7,200 × 48,000 × 2 × 4`로 약 **2.76 GB**다. 디코딩 결과 외에도 원본, 복사 버퍼, 인코더와 브라우저가 사용하는 메모리가 있다. 전체 파일을 한 번에 PCM으로 풀어 두는 경로는 긴 녹음의 기본 전략으로 적합하지 않다.

[MDN decodeAudioData 안내](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData)는 전체 파일 데이터가 필요하며 파일 조각은 지원하지 않는다고 설명한다. 임의 바이트 위치에서 컨테이너를 잘라 디코딩할 수 있다고 약속하지 않는다. MP3 프레임 처리에 성공한 경로도 MP4/M4A 인덱스나 Opus 페이지를 같은 방식으로 다룬다는 증거는 아니다.

압축 프레임을 순차 처리하고, 제한된 크기의 작업 버퍼와 동시 작업 수를 유지하는 안을 우선 검토한다. 불필요한 버퍼 복사와 전체 청크의 메모리 동시 보관을 줄인다. Web Worker는 화면 응답성을 위한 수단이며 메모리 사용을 없애는 수단이 아니다.

## 처리 기술 후보

| 후보 | 검토 이유 | 결정 전 확인 사항 |
| --- | --- | --- |
| WebCodecs와 컨테이너 demux | 순차 디코딩·인코딩 후보 | 코덱·브라우저·컨테이너별 지원과 시간 정확성 |
| ffmpeg.wasm | 여러 포맷 처리 후보 | 다운로드 크기, 메모리, 실행 시간, 배포 헤더, 라이선스와 유지 부담 |
| 지원 파일의 직접 재사용·추출 | 재인코딩 손실과 비용 절감 | 유효한 청크 생성, 컨테이너 구조, 제공자 수용 |

어느 도구도 확정하지 않았다. 합성 MP3 실험의 기술 선택을 제품 전체 미디어 라이브러리 선택으로 승격하지 않는다.

## 실패 처리 제안

파일 손상, 오디오 트랙 없음, 지원하지 않는 코덱, 자원 부족, 인코딩 파일 초과, 저장 할당량 초과를 구분한다. 초과 파일을 보낸 다음 오류를 기다리는 흐름은 피한다. 새 구간 계획이나 압축을 제안할 때 바뀌는 범위·품질·예상 추가 실행을 보여준다.

준비에 성공한 청크가 있더라도 저장 실패 상태를 성공으로 표시하지 않는다. 잠금 시 평문 오디오 버퍼와 작업의 처리 정책이 필요하다. 암호화된 체크포인트를 남기고 정지하는 방향은 제안이며 아직 검증하지 않았다.

## 검증 결과 VERIFIED TESTS

2026-09-30 MacBook Air의 기존 Chromium 151에서 합성 MP3를 순차 처리했다. 1시간 입력은 40.9초, JS heap 최대 61 MB, 2시간 입력은 86.1초, heap 최대 97 MB였다. 16개의 WebM/Opus 출력은 모두 디코딩됐고 최대 크기는 4.32 MB, 길이 오차는 6~14 ms였다. 브라우저 RSS 최대는 약 605 MB였다.

이는 오디오 준비 실험 결과다. 실제 말소리 정확도, 인증된 STT, 긴 실영상, 임의 브라우저의 성능·메모리 한계와 제품 코드의 성능은 입증하지 않는다. 최초 Chrome 154 시험 중단을 포함한 전체 조건은 [검증 기록](08-verification-and-release-gates.md)에 남겼다.
